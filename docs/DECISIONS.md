# Open decisions and risk register

Status: proposed defaults only. Commercial owner signs off before release 1 production use.

# 15. Design decisions requiring commercial sign-off

These are **not implementation blockers for Phase 0–2**, but must be decided before asserting production-grade scenario actionability:

1. **Default pricing conventions:** Which commodities/grades, quote units, and reference standards are first, and which conversion tables/authorities are approved?
2. **Commercial basis vocabulary:** Preferred delivery-term taxonomy; when are origin handling, delivered freight, or unloading included in buyer/seller prices?
3. **Firm quote standard:** What human evidence is needed to mark a bid/offer firm, and for how long is it valid?
4. **FX policy:** Resolved 2026-10-27: the Bank of Canada's daily USD/CAD rate as the reference rate, blocked when it is more than four days old (see the decision below).
5. **Loss/dockage and quality adjustments:** Which charges/quantity basis apply to specific commodities and grades?
6. **Border/compliance ownership:** Who is importer of record, who arranges customs broker, and which cost placeholders are required before trade approval?
7. **Data rights:** Which external prices/data are licensed for storage, commercial display and derivative modeling?
8. **Internal confidentiality:** Whether exact farm addresses or farmer private contacts can be viewed by all employees.
9. **Multi-tenant branding:** Resolved 2026-10-27: no white-label or multi-company use (see the decision below).
10. **Release governance:** Who can approve new trade economics and database/schema production changes?

**Proposed safe defaults:** CAD per MT reporting, manually verified quote data, manual freight, zero loss *only if explicitly acknowledged*, no automatic execution, one internal organization initially, and an organization-aware schema.

# 16. Risks and mitigations

| Risk | Mitigation |
|---|---|
| Stale buyer prices look executable | Quote status, timestamps, explicit owner verification, hard actionability gate |
| Wrong unit/FX conversion creates imaginary margin | Canonical typed values, source conversion table, exact decimal golden tests |
| Freight double-counting from delivery bases | Explicit cost inclusion and basis compatibility validator |
| AI introduces unreviewed financial logic | Pure engine, independent agent reviewer + human review, CI and versioned snapshots |
| Tenant data leakage | API membership checks, grants/RLS, authorization integration tests |
| Invalid geocoding exposes private farms | Confidence/precision, location redaction/generalization policies |
| Commercial feeds prohibited from reuse | Provenance and licensing registry before ingest |
| Over-building AI/automation before product-market fit | Phase gates; human-in-the-loop; no proprietary orchestration framework initially |
| Inability to restore critical trading records | Separate environments, backup verification and restore drills |
| Vendor lock-in | Standard Postgres, domain package isolated from Workers, Mapbox code kept in one map component, provider adapters |

# Dated architecture decisions

Proposed by the implementing agent; the owner accepts or reverses each one.

**2026-10-26 — TypeScript pinned to 6.0.x.** TypeScript 7.0 (the native compiler) is the current npm release, but typescript-eslint 8.72.1, the latest, declares `typescript >=4.8.4 <6.1.0`. Type-checked linting matters more than the newer compiler. Revisit when typescript-eslint supports 7.x.

**2026-10-26 — pnpm pinned to 10.28.0.** It is the version available and verified in the bootstrap environment; pnpm 12 is current. Upgrading is a separate, tested change.

**2026-10-26 — Prettier does not format Markdown.** Reformatting would rewrite the tables in the specification pack. Code, JSON, YAML and config files are formatted and checked in CI.

**2026-10-26 — API unit tests run in Node through Hono `app.request`.** No code uses Worker bindings yet, so Workers-runtime tests (`@cloudflare/vitest-pool-workers`) are deferred until it does; `wrangler dev` serves as the runtime smoke check. Worker globals are typed with `@cloudflare/workers-types` until bindings exist, then with `wrangler types` output, which Cloudflare now recommends.

**2026-10-26 — Staging deploys from GitHub Actions on each merge to `main`.** The workflow repeats the CI checks, runs `wrangler deploy --env staging` and smoke-tests `/api/v1/health`. The Cloudflare token and account ID are GitHub repository secrets read only by this push-triggered workflow, never by `pull_request` jobs, so pull requests from forks cannot reach them. Production gets a separate, approval-gated workflow when it is needed.

**2026-10-27 — One Worker serves the web app and the API.** On staging, `apps/api` serves the built `apps/web/dist` as static assets, with `/api/*` always routed to the Worker and other unknown paths falling back to `index.html`. One origin means no CORS and simpler session cookies when auth arrives. The top-level Worker config stays API-only for local development.

**2026-10-27 — shadcn/ui conventions set up by hand.** The shadcn registry was unreachable from the build session, so the `cn` helper, CSS-variable theme tokens and the two components in use (`Badge`, `Tabs` on Radix) were written in shadcn's style. `components.json`, the CLI and the `@/` import alias are added when the registry is first used.

**2026-10-27 — Narrow screens get a facility list, not the table.** Below Tailwind's `lg` breakpoint (1024 px) the workspace shows List and Map tabs and a stacked facility list, per the spec's "accessible list alternative", so prices never scroll off-screen. (Later: Map, Order book and Facilities tabs; see the workspace entries below.)

**2026-10-27 — Timestamps display in UTC.** Every quoted and valid-until time shows as `YYYY-MM-DD HH:MM UTC` until a display time-zone policy is decided.

**2026-10-27 — Web view types are provisional.** `apps/web/src/data/types.ts` serves the GT-010 shell only. The shared quote/facility contract is agreed and moved to `packages/domain` before quote work (GT-030) or the thin slice begins. (Done 2026-10-28: the quote contract is `packages/domain/src/quotes.ts`; `data/types.ts` stays as the workspace's own view, fed from it by `lib/workspaceQuotes.ts`.)

**2026-10-27 — Browser tests run in the required CI job.** Playwright tests in `tests/e2e` (desktop and phone) run against the built app served by `wrangler dev --env staging`, inside the existing `check` job, so branch protection covers them without a settings change. `@playwright/test` is pinned to 1.63.0 to match the Chromium preinstalled in the agent environment; CI installs the matching Chromium.

**2026-10-27 — Dependabot skips TypeScript 6.1 and later.** Its first npm run failed with `update_not_possible` because TypeScript 7 conflicts with typescript-eslint's supported range (see the 2026-10-26 TypeScript decision). Minor and patch npm updates are grouped into one weekly pull request.

**2026-10-27 — Supabase environments.** One hosted project, `gss-staging` (ref `nfwizbcpjpqxdoojfbdr`), on the free plan. Development and CI use a throwaway local Supabase started by the CLI, which `MASTER_PROJECT_SPECIFICATION.md` §4.4 allows. Production needs a further project, so a paid Supabase plan (which also adds daily backups and no idle pausing) is required before real trading data; the §10.4 restore drill comes with it.

**2026-10-27 — Database access model.** Application tables live in a private `app` schema that the Supabase Data API does not expose; browsers use Supabase only to sign in. The API Worker connects as `app_api`, a role with no superuser, no RLS bypass and only the grants each migration gives it. After verifying the caller's Supabase JWT, the Worker sets `app.user_id` for the transaction (`set_config(..., true)`), and row level security policies admit only rows of organizations where that user is an active member of an active organization. The database therefore trusts the Worker to set the user from a verified token; the Worker also filters by organization explicitly (§4.3). `app_api` is created without login; each environment enables it with its own password when the Worker first connects. If a role named `app_api` already exists with superuser, RLS bypass, role-creation, database-creation or replication rights, or with any role membership, the migration stops rather than reuse it. Database owners and administrator roles (`postgres`, `supabase_admin`) are outside this boundary and can read everything, so their credentials stay with operators and CI secrets only. How the Worker connects (Hyperdrive or the Supabase pooler) is decided with that work.

**2026-10-27 — Staging migrations from CI with a project-scoped secret.** After each merge, the Deploy staging workflow applies new migrations with `supabase db push --db-url`, using the `SUPABASE_STAGING_DB_URL` secret (the session-pooler connection string). This needs only that project's database password, not an account-wide Supabase access token that could reach other projects.

**2026-10-27 — Real data in `gss-staging` for now (owner's decision).** The owner chose to load the real buyer list into the one hosted project rather than buy a paid plan for a separate production project. Consequences accepted: no self-service backups on the free plan (the source spreadsheet stays the backup), the project pauses after about a week idle, and future migrations reach the real data directly after merge (each is still tested from scratch in CI first). Revisit before more users or data arrive; §10.4's restore drill remains outstanding.

**2026-10-27 — Sign-in: email, password and required TOTP, verified by Supabase Auth.** Supabase Auth with no self sign-up; administrators create users in the dashboard (since 2026-10-28, from the Team page; see below). Every user must enrol an authenticator app (TOTP) on first sign-in. The web app keeps the Supabase session and sends its access token to the API. The Worker checks each token by calling Supabase Auth (`GET /auth/v1/user`), which verifies the signature and that the session is still live, then requires the token's `aal` claim to be `aal2`, so skipping MFA in the browser does not get past the API. `/api/v1/health` is the only public API route; all others, including unknown ones, require sign-in. One Auth call per request is the cost; verifying against the project's signing keys (JWKS) with caching can replace it when traffic warrants.

**2026-10-27 — Worker to Postgres: postgres.js through the Supabase transaction pooler (staging later moved to Cloudflare Hyperdrive, below; `DATABASE_URL` remains the fallback without a Hyperdrive binding).** One short-lived connection per request (no prepared statements, TLS with certificate and host-name verification except for local databases), closed when the response is ready. The `DATABASE_URL` Worker secret, set in the Cloudflare dashboard and never in Git, holds the `app_api` pooler URL. Every query runs in a transaction that first sets `app.user_id` to the verified user, so row level security decides what is returned; a missing secret answers 500 `MISCONFIGURED` and a database failure 503 `DATABASE_UNAVAILABLE`. Cloudflare Hyperdrive can replace the per-request connection when latency matters.


**2026-10-27 — Counterparty directory and spreadsheet import (owner's request).** The owner asked to load their buyer list before the thin trade slice, which `docs/BUILD_PLAN.md` would otherwise put first; the import is kept minimal. Tables: `counterparties`, `counterparty_contacts`, `facilities`, `counterparty_logos`, `import_batches`. Any active member reads the organization's directory; operations and org_admin members create records (§2.1 "Edit counterparties"); nothing is edited or deleted through the API yet except replacing a logo. A legal name is unique per organization and country, ignoring case, so a re-import skips companies already listed instead of duplicating or changing them, and the same validated content cannot be imported twice. Rows with the same legal name and country become one counterparty with several contacts and locations. v1 accepts Canada and the United States only, with province and state codes. Instead of §9's staging table, the operator review is a server-side dry run shown in the app before anything is written; every row is validated by the same code in the browser and the Worker (`packages/domain`). Deferred: `risk_flags`, contacts' confidential scope, editing, and geocoding.

**2026-10-27 — Logos are PNG files stored in Postgres.** A logo is a `bytea` column next to its counterparty, so it is covered by the same row level security and audit trail as the record, with no second storage system. Only PNG up to 512 KB and 2048 px is accepted. The Worker checks the whole file (every chunk's CRC, IHDR fields, PLTE for palette images, consecutive IDAT that inflates to exactly the declared image size, IEND last, nothing after it) and stores a copy rebuilt from the critical chunks and a few colour chunks, so text or other data hidden in optional chunks is not kept (Codex review, 2026-10-28); the database checks signature and size; logos are served as `image/png` with `nosniff` and a sandboxing CSP, so an uploaded file cannot run as a page. SVG is not accepted. The browser fetches each logo with the user's token once per checksum, only when it scrolls into view. Supabase Storage can take over if logos grow larger or more numerous.

**2026-10-27 — Facility locations: latitude and longitude, plus a PostGIS point.** Coordinates are stored as entered (six decimals) with a required precision, `exact` or `approximate` (§6 location governance); imported coordinates are `approximate` unless the file says otherwise. A generated `geography(Point, 4326)` column with a GiST index serves later map queries. PostGIS is installed in the `extensions` schema.

**2026-10-27 — Audit trail starts with the directory (GT-016, minimal).** `app.audit_events` gets one row per insert, update or delete on directory tables, written by a trigger in the same transaction: organization, actor (`app.user_id`), action, entity, entity id, names of changed columns (never values) and the request id (`app.request_id`, also sent as the `X-Request-Id` response header). `app_api` has no access to it, so the API can neither read nor erase it. An audit view for admins (`GET /api/v1/audit`) and quote-revision auditing come later.

**2026-10-27 — Database TLS is verified (Codex review of ivanmueller/gss#11).** postgres.js `ssl: 'require'` encrypts but accepts any certificate in Node, so the API now uses `verify-full` (chain and host name), with a test against an impostor server presenting a self-signed certificate for another name. In the Workers runtime postgres.js hands TLS to `startTls()`, which verifies the certificate itself (checked locally in workerd: an impostor's certificate is refused before any credentials are sent), so this changes nothing on staging. Errors no route handles are now logged by type and request id only, and a malformed `DATABASE_URL` answers 500 `MISCONFIGURED` without being logged, because URL errors carry the whole string, password included.

**2026-10-27 — One organization: the owner's trading shop (owner's decision).** The platform serves one trading team. White-label tenants, multi-company features and an organization switcher are out of scope, and are removed from the specification's goals and Release 4. The `organizations` and `organization_members` tables stay as they are: membership is how the database limits records to the shop's active staff (an invited, suspended or unknown account sees nothing), and the existing isolation tests run in CI at no cost to anyone. The web app uses the user's first organization.

**2026-10-27 — The header shows the user's first name and last initial, never the email or the organization.** The API reads `first_name` and `last_name` from the user's Supabase metadata (display only; never used for access) and `GET /api/v1/me` returns them; the app shows e.g. "Signed in as Ivan M.", or "Signed in" when no name is set. Administrators set names in Supabase (README, Sign-in).

**2026-10-27 — The staging Worker reaches Supabase through Cloudflare Hyperdrive.** Supabase signs database and pooler certificates with its own root ("Supabase Root 2021 CA", `supabase/certs/`), which the Workers runtime does not trust and cannot be given, so direct connections from the Worker fail (logged as `kind=runtime_socket`; reproduced locally with a self-signed server). Hyperdrive makes the connection instead, verifying the certificate against that CA (`verify-full`, or `verify-ca` if the pooler's certificate does not name its host), to Supabase's session pooler on port 5432 as `app_api`. Query caching is off, because the API's queries return different rows per user. `scripts/setup-hyperdrive.js`, run by the manual workflow "Set up Hyperdrive (staging)", creates or updates the configuration from the `SUPABASE_HYPERDRIVE_URL` secret; the Worker uses its `HYPERDRIVE` binding when present and `DATABASE_URL` otherwise (local development and CI). The Cloudflare API token needs Hyperdrive and SSL and Certificates edit permissions for that workflow.

**2026-10-28 — Hyperdrive uses Supabase's session pooler; lost connections are retried once.** With Hyperdrive pointed at Supabase's transaction pooler (port 6543), about half of the staging requests failed with `CONNECTION_CLOSED`: Hyperdrive already pools in transaction mode, and a second transaction pooler behind it drops connections. `scripts/setup-hyperdrive.js` now always uses the session pooler (port 5432, same host and login) for a `*.pooler.supabase.com` host and caps Hyperdrive at 5 origin connections. The API also retries a read (GET) once on a fresh connection when the connection itself is lost (`CONNECTION_CLOSED`, `CONNECT_TIMEOUT` and similar). Writes are never retried: a lost connection does not say whether the write committed, and replaying a logo upload could undo someone else's later upload (Codex review, 2026-10-28). Closing the connection no longer delays the response.

**2026-10-27 — Map: MapLibre GL JS showing Mapbox map tiles (owner's decision; the viewer was later changed to Mapbox GL JS, below).** The specification leaves the tile provider open ("licensed production tile provider"). The owner chose Mapbox over MapTiler and self-hosted Protomaps: its free allowance covers a small team and allows commercial use, its satellite imagery shows elevators and rail sidings, and Mapbox documents using its tiles in MapLibre GL JS. The app keeps MapLibre, which is open source, rather than Mapbox GL JS, whose licence ties it to Mapbox; changing provider later means changing the map style, not the map code. Used through MapLibre, Mapbox bills per tile request rather than per map load, so usage is checked after the first week on staging. Mapbox sees which areas are viewed but never facility data: pins come from `GET /api/v1/facilities` and are drawn in the browser. The browser needs a public Mapbox token restricted to the app's addresses; how it reaches the build is settled with the map page (GT-023). Geocoding is not decided: results of Mapbox's default (temporary) geocoding may not be stored, and storing them needs its paid permanent geocoding.

**2026-10-27 — Map search: `GET /api/v1/facilities?bbox=` filtered by PostGIS through one function (GT-022).** The browser sends the visible box (`west,south,east,north` in degrees, checked by `parseBbox` in `packages/domain`); the Worker returns the organization's located facilities inside it, up to 5,000 (`truncated` beyond), and counts the facilities without coordinates, which no map can show. `app_api` still has no access to the `extensions` schema: the PostGIS test sits in `app.location_in_bbox()`, a function with a standard-SQL body (`return ...`) that Postgres resolves when the migration runs, so `app_api` needs only execute on it. It uses `ST_Intersects` on the planar longitude/latitude box, edges included; PostGIS's bare `&&` compares single-precision boxes and admitted points just outside. A box must have an area and must not cross the antimeridian (the browser sends two). Row level security applies first and PostGIS operators are not leakproof, so the spatial index is not used under it; the search scans one organization's facilities, which is fast at §10.4's 1,000. Not yet enforced: §6's rule that a farm's residential location appears on a map only with business need and permission. The directory holds buyers; a visibility rule comes before seller or farm locations are added.

**2026-10-27 — Map viewer: Mapbox GL JS instead of MapLibre GL JS (owner's decision; replaces the viewer part of the map decision above).** After the Mapbox tiles were chosen, the owner weighed MapLibre against Mapbox's own viewer and chose Mapbox GL JS, so the map uses one supported vendor end to end. `AGENTS.md`, the specification and the architecture notes now name it. Consequences accepted: Mapbox GL JS is not open source; its licence allows use only with Mapbox services while the organization holds a Mapbox account in good standing, and the viewer sends Mapbox limited de-identified usage data, which is how map loads are counted for billing (a free monthly allowance, then a charge per thousand loads). Changing provider later means replacing the map component, so Mapbox calls stay in that one component. Mapbox sees which areas are viewed but never facility data: pins come from `GET /api/v1/facilities` and are drawn in the browser. The browser uses a public token (`pk.`) restricted to the app's addresses, kept in the GitHub secret `MAPBOX_PUBLIC_TOKEN` rather than in Git and built into the web app; a secret token (`sk.`) fails the build. Geocoding is not decided: results of Mapbox's default (temporary) geocoding may not be stored, and storing them needs its paid permanent geocoding.

**2026-10-27 — Geocoding: Geocodio's free plan, reviewed before saving (owner's decision).** The owner's buyers have addresses but no coordinates, and the owner wants geocoding free. Mapbox's free (temporary) geocoding may not be stored and its permanent geocoding is paid; the U.S. Census and Natural Resources Canada services would need two integrations (and the Canadian licence was not confirmed); OpenStreetMap's Nominatim discourages bulk use. Geocodio's free plan covers 2,500 U.S. and Canadian lookups a day, and Geocodio states that results may be stored. Choices:
- The Worker looks addresses up (`POST /api/v1/facilities/geocode`) with the key in the Worker secret `GEOCODIO_API_KEY`, sent as a bearer header and never logged. Only address fields go to Geocodio (street, city, province or state, postal code, country), never names or contacts; logs carry Geocodio's HTTP status only.
- Precision: Geocodio's `rooftop`, `point`, `range_interpolation` and `nearest_rooftop_match` are `exact`; `street_center`, `place` and unknown types are `approximate`; `state` and `county` are too vague to save; a result in another country is dropped. Each saved point keeps `geocoding_source = 'geocodio'`, the accuracy type and the confidence.
- An operations or admin member reviews every result before saving. Results in another province or state, or below 0.80 confidence, start unticked.
- Saving (`POST /api/v1/facilities/coordinates`) accepts only matches the lookup signed: HMAC-SHA256 over the organization, facility, coordinates, precision, accuracy type, confidence and an expiry an hour ahead, with a key derived from the Geocodio key (no second secret; replacing the key voids unsaved results). So coordinates cannot be saved as Geocodio's unless Geocodio returned them, for that facility.
- The database lets operations and org_admin members fill in only the location columns, and only of a facility that has no coordinates (`20261027050000_facility_geocoding.sql`); geocoding never overwrites a location, and every save is audited. Correcting a location belongs to counterparty editing. (Changed 2026-10-28, below: editors may now correct a location by hand; a trigger keeps geocoding from overwriting coordinates.)
- One lookup covers up to 1,000 facilities; more are looked up after saving.

**2026-10-27 — The repository is public (owner's choice, recorded here).** Decided at the bootstrap (GT-001) and noted until now only in `docs/HANDOFF.md`: the specification asked for a private repository, but branch protection on a private repository needs a paid GitHub plan, so the owner kept it public with `main` protected by the required `CI / check`. Consequences: real business data (buyers, contacts, prices) and secrets never go into Git or into prompts; they live in `gss-staging` and in the GitHub, Cloudflare and Supabase secret stores. `AGENTS.md`, the specification (§1 and §10.1) and `docs/ARCHITECTURE.md` now say so. Revisit if the repository must become private.

**2026-10-27 — Design system, night theme and a left-menu app frame (owner's request).** The owner asked for a clean-slate layout and a token system that stays easy to change: a white, grey and black light theme and a matching night theme, no brand colour yet (and nothing depending on one), colour ramps for status colours, adjustable rounding, a standard spacing scale, four shadows and a professional typeface that is not the usual AI-generated look. Choices:
- Three token layers in `apps/web/src/styles/tokens/`: a palette of OKLCH ramps (50–950: neutral grey, blue, green, yellow, orange, red, teal, indigo; Tailwind CSS v4's values, MIT), colour roles per theme (`themes.css`), and scales plus the Tailwind bridge (`scales.css`). Tailwind's default colours, radii, shadows and font sizes are switched off so screens can only use the system's values. Roles follow shadcn/ui's names (`background`, `muted-foreground`, `primary` ...) so its components drop in; status roles are `info`, `success`, `caution` (yellow), `warning` (orange), `danger` and the trading roles `bid` and `offer`, each with text, subtle, border, solid and solid-foreground tokens. `styles/tokens.test.ts` fails if a role is missing from a theme, is not built from the palette, or drops below WCAG AA contrast in either theme.
- Rounding is one base value (`--radius-base`, 8 px) with multiples and per-component radii; spacing stays on Tailwind's 4 px grid; four shadows (`xs`, `sm`, `md`, `lg`) with their darkness set per theme.
- Typeface: IBM Plex Sans with IBM Plex Mono for prices and codes, both SIL OFL, bundled from Fontsource (`@fontsource-variable/ibm-plex-sans`, `@fontsource/ibm-plex-mono`) rather than loaded from Google. Inter is the most common startup interface font but also the default of most AI-generated designs, which the owner wanted to avoid; Plex is widely used in finance and data tools and has tabular figures. Changing font means changing `--font-sans` and the import in `main.tsx`. (Since 2026-10-28 prices use Figtree; see below.)
- Night theme: a cool slate blue-grey rather than black, matched to a dark map dashboard the owner pointed to (page `#252c36`, cards `#313842`); a `slate` ramp was added to the palette for it, while the light theme stays on neutral grey. One **Dark mode** switch in the profile menu (the owner wanted a toggle, not separate buttons); until it is used the app follows the device setting, then the switch's position is kept per browser in `localStorage` (`gss.theme`) and applied as the `dark` class on `<html>` by `lib/theme.ts`. An inline script in `index.html` applies it before the first paint; if a Content-Security-Policy is added later, it needs that script's hash. In the night theme, tints are see-through washes (`color-mix(... transparent)`) so they look the same on the page and on cards. Logos, the authenticator QR code and the Mapbox map keep their own light colours; the map pins copy the token values as hex, because Mapbox cannot read CSS variables.
- App frame: a fixed left menu (240 px) from 1,024 px up, a slide-over panel below; the top bar holds only the connection dot and the profile menu (the old "API reachable" text and "Signed in as" line are gone). Each page has an `<h1>` through `PageHeader`. Planned pages (bids and offers, scenarios, team) are listed greyed out and are not links. (Since built: Team and Bids & offers; only Scenarios is still listed as planned.)
- New dependencies: `@radix-ui/react-dropdown-menu`, `@radix-ui/react-dialog` and `@radix-ui/react-slot` (same Radix family as the tabs already used) for the profile menu, the phone menu panel and the `asChild` pattern, chosen for their keyboard and screen-reader behaviour.

**2026-10-27 — Workspace: the Mapbox map, a commodity picker and an order book (owner's request).** The owner asked for the real Mapbox map in the middle of the workspace, styled grey and white in the light theme and slate in the night theme like two reference dashboards, a commodity picker for one or several commodities, and an order book comparing buy and sell prices and spreads, styled after a reference flows panel. The order book's wording, colours, currency handling and layout were later changed at the owner's request (entries below). Choices:
- Still synthetic (until 2026-10-28, when live bids and offers replaced them with demo data off; entry below): no bids or offers exist yet, so the workspace keeps running on labelled synthetic fixtures (GT-025), extended to four commodities, nine fictional facilities with map coordinates and a few made-up prices besides the golden fixture, chosen to show positive, negative and blocked spreads and an expired quote. They are not market prices. Real counterparty locations stay on the Map page; they are never shown next to made-up prices.
- Order book: one book per commodity and grade, with live offers (lowest first) and bids (highest first), ties by time quoted. Live means firm or indicative and before valid-until; expired, withdrawn, superseded or past-due quotes are listed as "Not in the book". Prices are compared only within one currency. The gross spread is best bid minus best offer, computed exactly with `decimal.js` in `packages/domain` (`grossSpread`, `compareDecimal`) as `docs/TRADING_RULES.md` §5.3 asks, keeping the quoted decimal places. CAD against USD (or mismatched units) is blocked, never zero, until an FX source exists; a spread is labelled as before freight, FX and basis, not a margin, and indicative when either side is. Every price shows its quoted and valid-until times.
- Order book colours: the system's `offer` (teal) and `bid` (indigo) roles, each with a word, rather than the reference's green and red, because red means error in this design system and red against green is hard to tell apart for colour-blind users. One token change swaps them.
- Map: Mapbox's `light-v11` and `dark-v11` styles, repainted from new map tokens (`--map-land`, `--map-water`, borders, roads, labels) read from the page and converted to hex, because Mapbox cannot read CSS variables. Layers are matched by type and Mapbox's usual ids; anything else keeps Mapbox's look. The Map page's "Map" style follows the theme too, replacing `streets-v12`; satellite is unchanged. Pins are coloured by side (seller offer or buyer bid) and hollow for approximate locations. On the workspace the zoom buttons and attribution sit on the left and the starting view leaves room for the order book, which covers the map's right side from 1,280 px. Mapbox's zoom buttons and attribution are restyled with the tokens.
- `decimal.js` (10.6, MIT) is added to `packages/domain`, the library the trading rules name.
